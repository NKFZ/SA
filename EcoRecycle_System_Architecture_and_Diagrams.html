UC01: Unified Authentication & Register
การเข้าสู่ระบบแบบรวมศูนย์และการลงทะเบียนแยกบทบาท
All Roles
Primary Actor: ผู้ใช้ทุกกลุ่ม (Seller, Staff, Admin)
Stakeholders: ประชาชน, พนักงาน, ผู้ดูแลระบบ
Preconditions: เข้าถึงหน้าเว็บและมีอินเทอร์เน็ต
Postconditions: ได้รับ Auth Token, Role Session, สิทธิ์เข้าถึงหน้าแดชบอร์ดตามบทบาท
Trigger: ผู้ใช้กดปุ่ม Login หรือ Register บนหน้าเว็บ
Main Success Scenario:
  1. ผู้ใช้เลือกแท็บ Register: กรอก username, email, phone, password
  2. หากเลือกบทบาท Seller ต้องระบุที่อยู่ (Address) / หากเลือก Staff ไม่ต้องระบุที่อยู่ (ตามกฎข้อ 33)
  3. ระบบเข้ารหัสรหัสผ่าน และบันทึกลงตาราง users
  4. ผู้ใช้กรอก Username และ Password ในหน้า Login รวมศูนย์ (ไม่มีคำใบ้)
  5. หากกรอก admin / admin01 ระบบนำทางไปยังหน้า Admin Dashboard ทันที
  6. หากเป็น Seller หรือ Staff ระบบนำทางไปยังหน้าแดชบอร์ดของบทบาทนั้นๆ
Exception Flows: กรอกรหัสผ่านผิด → แจ้งเตือนข้อผิดพลาด / อีเมลหรือ username ซ้ำ → ปฏิเสธการลงทะเบียน
UC02: Request Pickup & Auto-Queue
การเรียกรถรับซื้อขยะและการจัดสรรคิวอัตโนมัติ
Seller
Primary Actor: Seller (ผู้ขายขยะ)
Stakeholders: Seller, Staff ที่รับงาน, ฝ่ายขนส่ง
Preconditions: เข้าสู่ระบบในสถานะ Seller และไม่มีคิวที่รอดำเนินการอยู่
Postconditions: สร้างตั๋วคิวสถานะ 'Waiting' และมอบหมายให้ Staff ที่มีคิวน้อยที่สุด
Trigger: Seller กดปุ่ม "เรียกพนักงานมารับขยะ"
Main Success Scenario:
  1. Seller เปิดหน้าเรียกรถ ระบบดึงที่อยู่และเบอร์โทรที่บันทึกไว้ขึ้นมาแสดง
  2. Seller ติ๊กเลือกประเภทขยะที่มี (พลาสติก, กระดาษ, แก้ว, โลหะ) และพิกัดรับขยะ
  3. Seller กดยืนยันการเรียกรถรับซื้อ
  4. ระบบตรวจจับพนักงาน (Staff) ที่มีคิวงานค้างน้อยที่สุดในระบบ (Least-Queue Algorithm)
  5. ระบบบันทึกคิวลง queue_requests พร้อมกำหนด collector_id
  6. ระบบแสดงสถานะคิว "กำลังรอพนักงานตอบรับ" พร้อมข้อมูลพนักงานที่ได้รับมอบหมาย
Business Rules: Seller มีคิวที่ยังไม่จบงานได้เพียง 1 คิวเท่านั้น (Single Active Queue Guard) หากมีค้างอยู่ปุ่มเรียกจะถูกปิดการทำงาน
UC03: Staff Dispatch & Navigation
การจัดการคิวงานและการเดินทางของพนักงาน
Staff
Primary Actor: Staff (พนักงานเก็บขยะ)
Stakeholders: Staff, Seller, ผู้จัดการฝ่ายปฏิบัติการ
Preconditions: เข้าสู่ระบบ Staff มีคิวงานที่ได้รับมอบหมายในระบบ
Postconditions: สถานะคิวเปลี่ยนเป็น 'In Progress' และเปิดหน้าประเมินขยะ
Trigger: Staff กดปุ่ม "ไปยังสถานที่รับขยะ" (Go To Location)
Main Success Scenario:
  1. Staff ดูรายการคิวงานที่ได้รับมอบหมาย ซึ่งจัดเรียงตามลำดับก่อนหลัง (FIFO Order)
  2. คิวแรกที่สถานะ 'Waiting' จะปลดล็อกปุ่ม "Go To Location" ส่วนคิวถัดไปจะถูกล็อก
  3. Staff กด "Go To Location" เพื่อเริ่มงานคิวนั้น
  4. ระบบเปลี่ยนสถานะคิวเป็น 'In Progress' และนำทางไปยังพิกัดของ Seller
  5. ระบบนำทาง Staff ไปยังหน้าแบบฟอร์มประเมินขยะ พร้อมแสดงชื่อ Seller ที่ให้บริการ
  6. ปุ่มทดสอบอัตโนมัติถูกนำออกอย่างถาวร (ตามกฎข้อ 32)
Business Rules: Staff สามารถรับงานและดำเนินการได้ทีละ 1 คิวเท่านั้น (1-Active Job Rule) คิวถัดไปจะเริ่มได้เมื่อคิวปัจจุบันปิดงานสมบูรณ์

UC04: Waste Evaluation & Weight Entry
การตรวจสอบ คัดแยก และบันทึกน้ำหนักขยะ 4 ประเภท
Staff
Primary Actor: Staff (พนักงานเก็บขยะ)
Stakeholders: Staff, Seller
Preconditions: Staff เดินทางถึงจุดรับขยะ มีคิวงานที่กำลังให้บริการอยู่
Postconditions: บันทึกรายการประเภทขยะ น้ำหนัก และคำนวณคะแนนรวมสำเร็จ
Trigger: Staff ตรวจสอบขยะ ณ จุดรับจริงและเปิดหน้าประเมิน
Main Success Scenario:
  1. ระบบแสดงชื่อ Seller ตรงจุด "ลูกค้าที่กำลังให้บริการ" อย่างถูกต้อง
  2. Staff ติ๊กเลือก Checkbox ประเภทขยะที่มีจริง (ขยะรีไซเคิล, ขยะอินทรีย์, ขยะทั่วไป, ขยะอันตราย)
  3. ช่องกรอกน้ำหนักถูกล้างค่าเริ่มต้นออกเป็นค่าว่าง (Staff ต้องชั่งจริงและกรอกเอง)
  4. เมื่อติ๊กเลือกประเภท ช่องกรอกน้ำหนักจะปลดล็อกให้กรอกตัวเลข (กิโลกรัม)
  5. ระบบดึงอัตราแต้มจาก waste_rates มาคูณน้ำหนักและแสดงคะแนนรวมทันที
  6. เมื่อติ๊กเลือกและกรอกน้ำหนัก > 0 สำเร็จ ปุ่มสร้าง QR จะปลดล็อก
Guards: หากไม่ติ๊กเลือกขยะเลย หรือใส่น้ำหนักเป็น 0 หรือค่าว่าง → ปุ่มสร้าง QR Code จะถูกปิดการทำงาน (Disabled)
UC05: Dynamic QR & Verification
การสร้าง Dynamic QR Code และการสแกนตรวจสอบสิทธิ์
Staff Seller
Primary Actor: Staff (ผู้สร้าง) และ Seller (ผู้สแกน)
Stakeholders: Seller, Staff, ฝ่ายความมั่นคงปลอดภัยระบบ
Preconditions: Staff มีคิวที่กำลังให้บริการ (กฎ 31) และกรอกน้ำหนัก > 0
Postconditions: Seller ได้รับ Modal สรุปรายการแต้ม และยืนยันการรับสิทธิ์
Trigger: Staff กดปุ่ม "สร้าง QR Code สำหรับลูกค้ารับแต้ม"
Main Success Scenario:
  1. Staff กดปุ่ม "Generate QR Code" ระบบสร้าง Dynamic Token พร้อมระบุ Target User ID
  2. ระบบตั้งเวลาหมดอายุ QR Code ภายใน 5 นาที (Single-use Expiring Token)
  3. Seller เปิดแอปมือถือ เลือกเมนู "สแกนรับแต้ม" และส่องกล้องไปยัง QR Code ของ Staff
  4. ระบบตรวจสอบความถูกต้อง: ตรวจว่า User ID ของผู้สแกนตรงกับ Target User ID หรือไม่
  5. หากถูกต้อง แสดง Modal สรุปยอดแต้ม ประเภทขยะ และชื่อพนักงานให้ Seller ตรวจสอบ
  6. Seller กดปุ่ม "ยืนยันรับแต้ม" (Accept Claim)
Security Rule: ป้องกันการสแกนข้ามคน (Scan ของคนอื่นไม่ได้) หาก User ID ไม่ตรง ระบบจะปฏิเสธการสแกนทันทีพร้อมแจ้งข้อผิดพลาด
UC06: Finalize Queue Transaction
การยืนยันการทำรายการและการปิดงานคิว
Staff Seller
Primary Actor: Staff และ Seller (การทำงานประสานกัน)
Stakeholders: Seller, Staff, บัญชีคะแนนสะสม
Preconditions: Seller ได้สแกน QR Code และกดยอมรับรายการบนหน้าจอของตน
Postconditions: บันทึกแต้มเข้าบัญชี Seller, เปลี่ยนสถานะคิวเป็น 'Completed', ปลดล็อกคิวถัดไปของ Staff
Trigger: ระบบได้รับสัญญาณการกดยอมรับจาก Seller
Main Success Scenario:
  1. ระบบล็อกปุ่มยืนยันของ Staff ไว้ จนกว่า Seller จะสแกนและกดยืนยัน (Decision Lock)
  2. เมื่อ Seller กดยอมรับ ระบบส่งสัญญาณอัปเดตแบบเรียลไทม์มายังหน้าจอของ Staff
  3. ปุ่ม "ยืนยันการเสร็จสิ้นงาน" บนหน้าจอ Staff ปลดล็อก
  4. Staff กดยืนยันเพื่อจบงานอย่างเป็นทางการ
  5. ระบบเพิ่มคะแนนเข้าบัญชี points_balance ของ Seller พร้อมบันทึกประวัติการขาย
  6. สถานะคิวเปลี่ยนเป็น 'Completed' และระบบปลดล็อกคิวลำดับถัดไปให้ Staff เริ่มงานใหม่ได้
Alternative Flow: หาก Seller กด "ปฏิเสธ" (Reject) → รายการถูกยกเลิก ไม่มีการโอนแต้ม สถานะเปลี่ยนเป็น 'Seller Rejected'

UC07: Redeem Eco Rewards
การแลกของรางวัลด้วยแต้มสะสม
Seller
Primary Actor: Seller (ผู้ขายขยะ/ประชาชน)
Stakeholders: Seller, ร้านค้าพาร์ทเนอร์, ผู้บริหารโครงการ
Preconditions: เข้าสู่ระบบ Seller มีแต้มสะสมในระบบ
Postconditions: แต้มสะสมถูกตัด สร้างโค้ดคูปอง/บันทึกการแลกรางวัล
Trigger: Seller กดเลือกของรางวัลในแคตตาล็อก
Main Success Scenario:
  1. Seller เปิดหน้าร้านค้าของรางวัล (Reward Catalog) ตรวจดูรายการของรางวัลและแต้มที่ต้องใช้
  2. ระบบแสดงแต้มคงเหลือปัจจุบันของ Seller
  3. Seller กดปุ่ม "แลกของรางวัล" ในรายการที่ต้องการ
  4. ระบบตรวจสอบเงื่อนไขความเพียงพอของแต้ม (Points Sufficiency Check)
  5. หากแต้มเพียงพอ ระบบหักคะแนนสะสมออกจาก points_balance
  6. ระบบบันทึกรายการลง redemptions และสร้างรหัส Voucher Code สำหรับนำไปใช้รับสิทธิ์
Business Rules: ถ้าแต้มไม่พอจะไม่สามารถแลกของได้ (Insufficient Points Guard) → ปุ่มแลกจะถูกปิดการทำงาน หรือระบบแจ้งเตือนว่าแต้มไม่พอ
UC08: View History & Audit Logs
การตรวจสอบประวัติการขายและประวัติการทำงาน
Seller Staff
Primary Actor: Seller และ Staff
Stakeholders: Seller, Staff, ฝ่ายตรวจสอบความโปร่งใส
Preconditions: เข้าสู่ระบบในบทบาทของตน
Postconditions: แสดงรายการประวัติย้อนหลังพร้อมรายละเอียดครบถ้วน
Trigger: ผู้ใช้คลิกแท็บ "ประวัติการขาย" หรือ "ประวัติการทำงาน"
Main Success Scenario:
  1. สำหรับ Seller: เข้าหน้า "ประวัติการขายของฉัน" (Sales History)
    • แสดงรายการประวัติการขายแต่ละครั้ง
    • แสดงวันเวลา, สถานที่/พิกัดที่ขาย, ชื่อ Staff ผู้รับซื้อ, รายละเอียดประเภทและน้ำหนักขยะ, และคะแนนที่ได้รับ
  2. สำหรับ Staff: เข้าหน้า "ประวัติการทำงาน" (Work History)
    • แสดงรายการประวัติการเก็บขยะที่เสร็จสิ้น
    • แสดงวันเวลา, สถานที่, ชื่อลูกค้า (Seller), รายละเอียดขยะ และคะแนนที่บันทึก
  3. ผู้ใช้สามารถคลิกดูรายละเอียดแยกแต่ละหมวดขยะในแต่ละใบเสร็จได้
Data Integrity: ข้อมูลประวัติดึงจากความสัมพันธ์เชื่อมโยง queue_requests ร่วมกับ waste_transactions และ users
UC09: Admin Rates & Clean Queues
